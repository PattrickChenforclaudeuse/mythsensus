🚨 Critical Findings
SEC-C01 • PDPA Compliance
No PDPA Consent Mechanism for Sensitive Personal Data
mythsensus-schema.sql • mythsensus-interactive.html
Critical ▼

Description

Mythsensus collects name, dob, birth_time, birth_place, and gender. Under Thailand's PDPA (Personal Data Protection Act), birth date and astrological/religious-belief-related data may qualify as sensitive personal data (Section 26) which requires explicit consent before collection.

Currently the schema has no consent_given_at timestamp, no consent version tracking, and the HTML mockup has no consent checkbox or privacy notice before data collection.

Impact

PDPA violations carry fines up to 5 million THB and potential criminal penalties. Users in Thailand have the right to withdraw consent, request data deletion, and file complaints with the PDPC. Without a consent mechanism, the entire user data collection flow is non-compliant.

Recommended Fix

1. Add consent_given_at timestamptz and consent_version text columns to the users table.

2. Add a privacy_consents table tracking purpose, consent date, withdrawal date.

3. Implement a mandatory consent checkbox + privacy notice before birth data form submission.

4. Add a "Delete My Data" feature (Right to Erasure) in user settings.

5. Create a public Privacy Policy in Thai and English.

SEC-C02 • Data Exposure
PDF Reports (pdf_url) Potentially Accessible Without Auth
mythsensus-schema.sql • reports table
Critical ▼

Description

The reports table stores pdf_url as a plain text URL. If PDFs are stored in Supabase Storage or a public CDN bucket, the URL alone may grant access to anyone who has it. PDF reports contain full PII: name, birth date, birth time, birth place, gender, and detailed personality analysis.

There is no indication of signed URLs, expiration tokens, or access control on the storage level.

Impact

If a PDF URL is leaked, shared, or indexed by search engines, any person in the world could view another user's birth chart report containing all their personal data. This constitutes a data breach under PDPA.

Recommended Fix

1. Store PDFs in a private Supabase Storage bucket (not public).

2. Generate signed URLs with expiration (e.g., 1-hour TTL) via an authenticated API endpoint.

3. Add RLS on the storage bucket so only the profile owner can access their PDFs.

4. Never store the raw public URL in the database — store the storage path instead.

-- Example: Store path, not URL
ALTER TABLE public.reports
  RENAME COLUMN pdf_url TO pdf_storage_path;
-- Then generate signed URLs in the API layer:
-- supabase.storage.from('reports').createSignedUrl(path, 3600)
SEC-C03 • Data Retention
No Data Retention Policy or Automated Deletion
mythsensus-schema.sql • All tables
Critical ▼

Description

The FAQ states "Birth data is used solely for report generation and is not retained beyond the session." However, the schema permanently stores all PII in the profiles table with no TTL, no auto-deletion, and no data lifecycle management.

This contradicts the stated privacy commitment and violates PDPA's data minimization principle.

Impact

Users trust that their data won't be retained. If breached, the entire historical database of birth data would be exposed. This is also a legal liability — the stated policy doesn't match actual practice.

Recommended Fix

1. Decide: either update the FAQ to honestly state data is retained for service delivery, or implement actual session-only processing.

2. If retaining: add data_retention_until column, implement a cron job to purge expired data.

3. Implement a "Right to Be Forgotten" API endpoint that cascades through profiles, reports, god_draws, etc.

4. Encrypt PII columns at rest using Supabase Vault or pgcrypto.

SEC-C04 • XSS
Widespread innerHTML Usage Without Sanitization
mythsensus-interactive.html • Lines 564-642
Critical ▼

Description

The interactive homepage uses innerHTML += extensively to render dynamic content including systems grid, score bars, feature cards, pricing cards, benefits, and FAQ items. While the current data is hardcoded in JavaScript constants, this pattern is dangerous because:

1. If any of this data is ever loaded from Supabase or an API (e.g., dynamic pricing, user-generated content), it becomes a Stored XSS vector.

2. The FEATURES array already contains raw HTML in the body field, which is injected directly via innerHTML.

3. The promo code input value is not sanitized before potential server-side processing.

Impact

An attacker who can modify any data source (e.g., compromised CMS, API MITM, or god blessing text from JSON) could inject malicious scripts that steal session tokens, redirect to phishing pages, or mine cryptocurrency in the user's browser.

Recommended Fix

1. Replace innerHTML with textContent for any user-facing data.

2. Use document.createElement() + textContent for dynamic DOM construction.

3. If HTML rendering is necessary, use DOMPurify to sanitize all input.

4. Add Content Security Policy (CSP) headers to block inline scripts.

<!-- Add DOMPurify -->
<script src="https://cdnjs.cloudflare.com/ajax/libs/dompurify/3.0.6/purify.min.js"
  integrity="sha384-..." crossorigin="anonymous"></script>

// Then sanitize:
g.innerHTML += DOMPurify.sanitize(htmlString);

SEC-H01 • Access Control
Missing users INSERT Policy — Registration May Fail or Be Exploitable
mythsensus-schema.sql • Line 148-151
High ▼

Description

The users table has SELECT and UPDATE RLS policies but no INSERT policy. The fn_handle_new_user() trigger uses SECURITY DEFINER which bypasses RLS for the trigger, but any direct client-side insert attempts would be blocked.

More critically, there is no DELETE policy on users, meaning users cannot delete their own accounts (PDPA Right to Erasure issue).

Impact

Account deletion flow will fail silently. If a user requests data deletion under PDPA, the system has no mechanism to comply.

Recommended Fix

Add a DELETE policy for users to delete their own account. Use CASCADE to clean up related data.

CREATE POLICY users_delete ON public.users
  FOR DELETE USING (auth.uid() = id);
SEC-H02 • Rate Limiting
No Rate Limiting on God Draws or Organum Sessions
mythsensus-schema.sql • god_draws, organum_sessions
High ▼

Description

The god_draws table has an INSERT policy but no rate limit constraint. A user could rapidly insert thousands of draws to farm all 200 gods, bypassing the intended "1 draw per day" free tier limit. The same applies to organum_sessions (intended: 5/day for free users).

There are no database-level constraints, no application-level middleware, and no Supabase Edge Function rate limiters defined.

Impact

Paid features (unlimited draws for subscribers) become worthless if free users can bypass limits. Revenue impact for a product monetized on engagement limits.

Recommended Fix

1. Add a database function that checks draw count before INSERT.

2. Alternatively, use Supabase Edge Functions with rate limiting middleware.

3. Add a unique index on (user_id, drawn_at::date) for god_draws to enforce 1 per day at DB level.

-- Enforce 1 god draw per day at DB level
CREATE UNIQUE INDEX idx_god_draws_daily
  ON public.god_draws (user_id, (drawn_at::date));

-- For organum: create a check function
CREATE OR REPLACE FUNCTION check_organum_limit()
RETURNS TRIGGER AS $$
DECLARE
  today_count int;
  user_plan text;
BEGIN
  SELECT plan INTO user_plan FROM public.users WHERE id = NEW.user_id;
  IF user_plan = 'free' THEN
    SELECT count(*) INTO today_count FROM public.organum_sessions
    WHERE user_id = NEW.user_id AND asked_at::date = CURRENT_DATE;
    IF today_count >= 5 THEN
      RAISE EXCEPTION 'Daily organum limit reached';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
SEC-H03 • PII Encryption
PII Stored as Plaintext — No Encryption at Rest
mythsensus-schema.sql • profiles table
High ▼

Description

All PII fields (name, dob, birth_time, birth_place, gender) are stored as plaintext. While Supabase uses encrypted disks at the infrastructure level, there is no application-level encryption, meaning anyone with database access (admin, backup leak, SQL injection) sees all PII in the clear.

Impact

A database compromise exposes all user birth data in cleartext. Birth date + name + birthplace is sufficient for identity theft in many jurisdictions.

Recommended Fix

1. Use Supabase Vault (pgsodium) to encrypt PII columns.

2. At minimum, use pgcrypto to encrypt birth_time, birth_place, and name.

3. Implement envelope encryption — encrypt data with a DEK, encrypt DEK with a KEK stored in Vault.

SEC-H04 • CDN Integrity
Google Fonts CDN Loaded Without Subresource Integrity (SRI)
mythsensus-interactive.html • Lines 7-9
High ▼

Description

Three Google Fonts resources are loaded without integrity hashes or crossorigin attributes on the CSS link tag. If Google's CDN is compromised or a DNS hijack occurs, malicious CSS (or even JS via CSS expressions in older browsers) could be injected.

Impact

Supply-chain attack vector. A compromised CDN could inject CSS-based data exfiltration (e.g., reading input values via attribute selectors and background-image URLs).

Recommended Fix

1. Self-host the fonts (you already have Sarabun embedded as base64 — do the same for Cinzel, Cormorant, Josefin Sans).

2. If using CDN, add integrity="sha384-..." and crossorigin="anonymous".

3. Implement CSP with style-src that whitelists only specific origins.

SEC-H05 • SECURITY DEFINER
SECURITY DEFINER Functions May Bypass RLS Unexpectedly
mythsensus-schema.sql • Lines 218-230, 246-261
High ▼

Description

Two functions use SECURITY DEFINER: fn_update_longest_streak() and fn_handle_new_user(). SECURITY DEFINER functions run with the permissions of the function creator (typically superuser), bypassing all RLS policies.

While fn_handle_new_user() correctly sets search_path = public, fn_update_longest_streak() does not set search_path, making it vulnerable to search path injection attacks.

Impact

An attacker could create a malicious streaks table or function in a different schema that gets resolved before public.streaks, potentially escalating privileges.

Recommended Fix

Add SET search_path = public to fn_update_longest_streak(). Also review if SECURITY DEFINER is truly necessary — consider SECURITY INVOKER where possible.

LANGUAGE plpgsql
SECURITY DEFINER

SEC-H06 • CSP Missing
No Content Security Policy Headers Defined
All HTML files • Vercel deployment config
High ▼

Description

None of the HTML files include CSP meta tags, and there is no vercel.json or server config defining CSP response headers. Without CSP, any XSS vulnerability can execute arbitrary JavaScript, load external scripts, or exfiltrate data.

Impact

CSP is the last line of defense against XSS. Without it, even a single innerHTML injection can fully compromise the user session.

Recommended Fix

Add CSP headers in Vercel deployment config:

// vercel.json
{
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        {
          "key": "Content-Security-Policy",
          "value": "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self' https://*.supabase.co"
        },
        {
          "key": "X-Content-Type-Options",
          "value": "nosniff"
        },
        {
          "key": "X-Frame-Options",
          "value": "DENY"
        }
      ]
    }
  ]
}

SEC-M04 • Payment Security
No Payment Webhook Signature Verification Defined
Architecture • Lemon Squeezy integration
Medium ▼

Description

The project plans to use Lemon Squeezy for payments ($19 one-time, $5/mo subscription). There is no webhook handler code, no signature verification logic, and no idempotency checks.

Impact

Without webhook signature verification, an attacker could forge payment confirmation requests to get free reports. Without idempotency, duplicate webhook deliveries could create duplicate orders.

Recommended Fix

1. Implement Lemon Squeezy webhook signature verification using HMAC.

2. Add an orders table with idempotency keys to prevent duplicate processing.

3. Never trust client-side payment status — always verify server-side.

SEC-M05 • Auth
No Email Verification Required Before Data Access
mythsensus-schema.sql • fn_handle_new_user()
Medium ▼

Description

The fn_handle_new_user() trigger creates a user row immediately on signup. There is no check for email verification status. An attacker could create accounts with fake emails and access free-tier features. Since Supabase Auth supports email verification, it should be enforced.

SEC-M06 • Plan Escalation
Users Can UPDATE Their Own Plan Column
mythsensus-schema.sql • users_update policy
Medium ▼

Description

The users_update RLS policy allows users to update any column in their own row, including plan. A user could change their plan from 'free' to 'subscriber' using the Supabase client directly, bypassing payment entirely.

Impact

Complete revenue bypass. Any free user can self-upgrade to subscriber by running a single Supabase client call.

Recommended Fix

1. Restrict the UPDATE policy to only allow updating display_name.

2. Move plan changes to a SECURITY DEFINER function that verifies payment status.

-- Restrict update to display_name only
CREATE POLICY users_update ON public.users
  FOR UPDATE
  USING (auth.uid() = id)
  WITH CHECK (
    auth.uid() = id
    AND plan = (SELECT plan FROM public.users WHERE id = auth.uid())
  );
